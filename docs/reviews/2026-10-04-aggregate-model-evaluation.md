本评估判定：**Critical=0，Major=6，Minor=3**。其中路由改指、存量模型丢失和账号绑定绕过已有实际失败核验；其余请求链路问题为源码可证，影响在所列触发条件下成立。独立审查通过本报告，只表示评估材料达到交付要求，不表示 cc-switch 功能已修复或产品验收通过。

## 合理性、实用性与现有优点

架构分工基本正确：聚合卡片保存路由表，不重复保存端点和凭据；目标供应商继续负责协议适配。后端保存校验、目标删除保护和禁嵌套限制有助于避免悬空引用及路由循环。`aggregate.rs` 还处理 `[1m]` 后缀、模型名 trim、别名匹配、默认模型置顶和目录合成，已有有意义的单元测试。

使用场景包括：同一客户端内手动选择不同供应商模型；为团队提供易读的模型别名；在主任务模型与内部辅助请求之间安排不同路由；把现有 API-key 供应商和已登录的官方账号放入一个模型目录。当前功能主要是**按名称分流**，并没有实现基于任务难度自动选模型、负载均衡或成本最优调度。未命中路由的兜底也不等于调用失败后的自动故障转移。

Claude 的供应商卡片适合按供应商整理四种客户端档位，增加新卡时实际会自动展开，新增模型也会展开，初步配置流程是可用的。Codex 的“客户端名称 → 供应商 → 上游名称”表格更直接。模型列表按供应商缓存、默认显示名带供应商名称，以及聚合模式隐藏无意义的端点/密钥字段，都应保留。

两种客户端可以共享路由结果、目标验证和状态观测的逻辑；没有必要强行共用一张编辑表。Claude 的兼容 ID/档位/能力表与 Codex 的客户端 slug/目录协议是不同约束。

## 主要问题

### M01 / P1：显示顺序会改变已有路由 ID 对应的上游

证据：`src/utils/aggregateRoutes.ts:195` 的 `assignSlotIds` 每次按当前数组位置重新生成所有 ID；`AggregateProviderFields.tsx:170` 的每次 commit 都调用它，卡片排序也经该路径提交。`src/types.ts` 却将 routeId 描述为“持久化，稳定的路由键”。

触发示例：A 的 `claude-sonnet-4-6` 映射到 upstream-a，B 的 `claude-sonnet-4-5` 映射到 upstream-b；交换卡片顺序后，`claude-sonnet-4-6` 映射到 upstream-b。表内默认值和别名虽然跟随重编号，已有客户端会话、脚本或缓存携带的旧 ID 不会随之修改。选项外观排序因此可能改变请求目的地、计费与数据接收方。

实际核验：`.agent-org/evidence/aggregate-risk.test.ts` 第一项失败，原 ID 实际命中 upstream-b。建议保留合法既有 ID，只为新增槽位分配未使用 ID；显示顺序独立存储。删除后避免立即把旧 ID 分给不同模型。非法历史 ID 只在显式迁移时转换，先生成备份和变更预览。兼容 ID 的能力档位分配不能再靠无提示的拖拽顺序决定。

### M02 / P1：编辑存量数据会静默删掉同供应商同档位的多个模型

证据：`src/utils/aggregateRoutes.ts:151` 的 `groupSlotsByProvider` 只保留同一 provider+tier 的第一个槽位，`flattenProviderGroups` 无法恢复其余槽位。编辑器的卡片提交调用这条转换路径。后端当前验证只要求路由 ID 唯一，没有禁止同一供应商同一档位包含多个不同模型，因此这是可保存的数据形状，而非必定非法的配置。

实际核验：第二项兼容性测试失败，两个模型经过分组/展平后只剩一个。建议编辑器完整保留这些槽位，并支持同档位多行；若产品坚持每档位一行，至少显示迁移冲突、提供保留/导出/明确删除选择，在用户决定前阻止覆盖保存。不能以“UI 现在造不出来”作为删除旧数据的理由。

### M03 / P1：Codex 官方供应商作为 providerId 兜底时，错误进入普通登录校验

证据：`src-tauri/src/aggregate.rs:1562` 的 providerId 兜底返回 `(target,None)`；`handler_context.rs:341` 转换后只留下 `aggregate_override: Option<String>`。本地 `forwarder.rs:1367` 将 `is_none()` 当成“非聚合”进入官方客户端登录校验；`:2125` 又只有 `is_some()` 才注入托管 OAuth。

聚合 seed 使用 PROXY_MANAGED 占位认证。未命中槽位且兜底选官方供应商时，因为不需要改写模型名而得到 None，**请求会在普通登录校验中被拒绝，不能走预期托管认证**。现有占位符保护也会阻止相关占位符出站；本报告不声称真实凭据泄露或占位符已发送给官方服务器。slotId 命中可以正常进入注入分支，并不能覆盖 providerId 兜底。

建议显式传递“这是聚合请求”的路由来源，认证依据请求来源和目标认证类型决定，模型名是否改写单独决定。覆盖精确匹配、providerId 兜底、slotId 兜底、普通官方直连四种情况；完整链路测试应验证选对账号、请求头、最终模型和普通直连行为。

### M04 / P0：账号绑定失效后，可回落到另一份本地登录凭据

证据：本地 `forwarder.rs:163–198` 先按绑定账号查 Manager，但任意 Manager 错误都会调用 `read_codex_auth_json_fallback`；该函数只检查 auth_mode 与非空 token，没有验证它属于该供应商绑定的账号，也允许 workspace ID 为空。绑定账号不存在与“未绑定、允许用默认账号”因此被混为一种回落。

实际核验：在独立临时用户目录放入一个**模拟、无效**的 unrelated workspace 登录文件，运行既有 `aggregate_official_target_with_dangling_account_reports_login_hint` 测试。原本应拒绝 dangling 绑定，实际返回该无关 workspace 的模拟 token，测试失败。这证明选择边界被绕过，不代表本次发送了真实网络请求。

建议显式绑定失败时直接返回明确登录/绑定错误；未绑定时才允许显式配置的默认来源。若保留文件回落，必须验证账号/workspace、令牌有效性与所选凭据来源，不能悄悄选择另一个账号。相关测试统一隔离所有文件入口，禁止失败消息打印 token 或整段认证元组。此项先于扩大官方账号支持范围处理。

### M05 / P1：聚合截断为一个目标后，目标熔断检查被跳过

证据：`handler_context.rs:366` 截断 providers 至一个，注释约定“目标熔断即不可用，显式失败”；`forwarder.rs:621` 则仅根据 `providers.len()==1` 设置 bypass，`:644` 跳过目标的 allow_provider_request。此前 router 检查的是被选择的逻辑供应商，不等于聚合解析后目标的熔断检查。

因而“不开聚合层故障转移”和“绕过目标熔断”被耦合。目标断路器已打开时仍会发起请求，可能增加等待、失败调用与无意义重试。该结论为源码路径核验，未对真实上游制造故障。

建议保留单目标、无自动跨供应商故障转移，但显式检查所选目标健康/熔断许可。普通单供应商历史策略与聚合策略分开定义；HalfOpen 许可只获取一次，并在成功、失败、取消后正确释放。测试以模拟传输统计实际调用数：Open 应为 0，HalfOpen 应服从许可数量。

### M06 / P1：Claude 选择“模型槽位兜底”，实际只选供应商

证据：`aggregate.rs:1513–1529` 的 Claude SlotId 兜底只取 providerId，并返回 None；Codex `:1572` 对 SlotId 保留该槽位 upstream。Claude 进入 `forwarder.rs:1426` 的目标普通映射后，可能选目标自己的另一个档位，或在目标没有请求档位/别名时触发 `route_unknown`。

界面展示的是“供应商 · 模型 (routeId)”兜底选项，用户会合理预期用该模型。比如兜底指定 A 的推理模型，未命中请求包含 haiku 档位时，目标自己的 haiku 路由可能另选模型；未知非安全模型还可能失败。不是所有内部请求都会失败，但“兜底槽位保证用其模型”并不成立。后端 Codex 注释“与 Claude 同款”也与实际代码不符。

建议明确三种行为：未知模型拒绝、交给目标供应商自身规则、固定模型兜底。SlotId 表示固定模型时应返回该槽位的 upstream，ProviderId 表示供应商规则时保留请求模型，UI 用不同说明显示。修改前补充标题/摘要/子任务等内部调用和未知模型的测试，避免一概把辅助调用错误强行发给任意模型。

## UI/UX 问题与设计建议

**U01 / Minor：Codex 默认引用不随重命名/删除维护。** `CodexAggregateFields.tsx:63–73` 只修改 slots。浏览器把 team-smart 改成 team-smart-renamed 后，两个默认下拉显示空白，而提交数据仍保存 team-smart。后端会拒绝悬空兜底，默认模型则可能被静默忽略，因此不是无校验的数据损坏，但用户需要自行猜测原因。建议重命名时同步本表默认引用；删除被引用行时提示重新选择或明确清空，并在对应字段显示错误。

**U02 / Minor：能力提示容易误导。** Claude 的思考阶梯由兼容 routeId 决定，不能证明上游真实支持思考参数；1M 开关也是声明。当前 sonnet-4-5 行显示“思考开关”，但禁用上限控件的 tooltip 却称“溢出 ID、无思考控件”（组件约第905行）。建议分别说明客户端可见控件与已验证的上游能力，区分“只支持开关”和“不支持”，显示 capability 数据的来源/版本。不要用自动 ID 把模拟或真实非 Claude 模型包装成已验证的 Claude 能力。

**U03 / Minor：编辑页基础操作与高级路由混在一起，名称仍有歧义。** 本次 1280px 预览中，供应商卡片、获取模型、增删行可以操作，但名称输入较窄，长模型名截断；Codex 同屏四列还加拉取按钮。别名规则在基本映射之前出现，增加初次理解成本。当前预览未覆盖小窗口或系统缩放，因此不宣称响应式已失败。建议主流程先映射，再选启动默认/未匹配请求处理；别名和能力覆盖放入高级区域。使用“客户端名称”“上游实际模型”“未匹配请求”“启动默认模型”等明确标签，并提供一条示例请求的路由预览。

建议使用分层界面：

1. 选择已有供应商，选择/输入上游模型，填写客户端显示名；新增时自动展开。
2. 设置启动默认模型；单独设置未匹配请求策略，解释它不是失败转移。
3. 高级区设置别名、客户端能力上限与上下文声明；带说明和来源。
4. 保存前展示变更：新增/删除/改指的路由、默认值、账号来源、需重启的客户端；高影响迁移须明确确认。
5. 保存后标示“已保存”“已写客户端配置”“需重启”“连接检查结果”，不同状态分别表达。连接检查应由用户主动触发，费用与账号可见，不能保存即自动发送模型请求。

这些建议应先以小范围表单修订验证，无需重做整个供应商管理页面。

## 最小架构改善方案

在现有 handler → forwarder 数据流增加一个小型、明确的路由结果，包含逻辑聚合供应商 ID、实际目标供应商 ID、匹配方式（精确/别名/模型兜底/供应商兜底）、原请求名称及可选 upstreamModel。认证、目标熔断和状态显示分别读取它需要的字段。两种客户端仍按各自协议解析和写目录。

路由标识作为持久配置身份保存，显示顺序与能力声明独立。模型目录、别名和默认值引用统一校验，并输出字段级错误。路由策略、客户端协议转换与账号凭据解析分别负责自己的边界，但继续复用原来的供应商和适配器；不引入一个可无限嵌套的路由框架。

观测同时保留“用户选中的聚合卡”和“本次请求实际上游”，不要为了抑制故障转移而只靠覆盖 current_provider_id。现有代码已经抑制成功后切走聚合卡，不能把这个已经处理的行为重复列为确定缺陷。费用现有 response_processor 优先使用返回模型/出站模型，应增加聚合专项验证；本报告没有证明当前费用归因错误。

## 效率和成本判断

聚合多一次本地查表和目标读取，对小型路由表应优先保持简单线性实现；本次没有运行延迟基准，不能给出新增多少毫秒或节省百分比。先修身份和路由正确性，再按真实请求记录评估性能，暂不引入缓存一致性、并发调度或动态最优选型算法。

按任务选择合适上游、为辅助请求安排能胜任的较低成本模型，可能减少模型费用，但聚合本身不会减少 token，也不保证更便宜。模型调用价格、订阅限制、网关收费、质量导致的重试都影响结果。本报告不引用未核实的实时价格，不估算未经计费证据支持的节省额。

优先实施确定性回归和本地模拟传输，真实账号端到端用最小样本验收。这比在每个修复阶段反复运行大规模真实模型任务更可控。修复 ID/账号/兜底错误还能减少错误请求、诊断和用户返工，其实际收益需要上线前后同类样本证明。
